# Сервер чек-листа

`migration.sql` — один транзакционный скрипт для новой установки и обновления старой схемы. Он сохраняет записи `checklist_entries` / `checklist_customers_log`, разрешает секцию `status` и закрывает прежний прямой доступ. Остальные таблицы общего проекта не затрагиваются. Повторный запуск допустим; PIN и история сохраняются. Supabase CLI в рабочем окружении не установлен, поэтому файл предназначен для SQL Editor, а не выдаётся за автоматически созданную CLI-миграцию.

## Установка / обновление

1. Сделайте резервную копию существующих записей. В Supabase Dashboard → SQL Editor выполните **весь** `migration.sql` от `postgres`. Нельзя выполнять части по очереди: доступы и функции должны меняться одной транзакцией.
2. В настройках Data API оставьте открытой схему `public`; `checklist_private` в Exposed schemas не добавляйте. Прямой REST-доступ к таблицам чек-листа закрыт. Это ожидаемо: браузер работает только через RPC.
3. В SQL Editor создайте **новые** PIN отдельно для каждого пользователя:

   ```sql
   select checklist_private.provision_user('agnesa');
   select checklist_private.provision_user('oksana');
   select checklist_private.provision_user('owner');
   ```

   Каждая команда выдаёт случайный восьмизначный PIN. Передайте его соответствующему человеку лично и сохраните в менеджере паролей. Не копируйте PIN в Git, конфигурацию сайта, публичные документы или скриншоты. Значение хранится в БД только как bcrypt (cost 10). Повтор этой команды **меняет PIN и отзывает все сессии этого пользователя**. Пароль не нужно вводить в SQL-запрос: он генерируется на сервере.
4. В `js/config.js` настройте URL проекта и **publishable** key. Не используйте там `service_role`, PIN или Telegram token.
5. Опубликуйте новую версию frontend вместе с серверным обновлением. Старый frontend после закрытия таблиц работать не будет. Проверьте вход каждого пользователя, отметку задачи, причину, отмену, приход/уход и отображение владельцу на втором устройстве.

Старые публичные PIN больше не принимаются. До provisioning вход закрыт. Самостоятельная регистрация отсутствует: пользователей/роли задаёт оператор БД. Имя связано с историческими записями; при переименовании пользователя нужна отдельная миграция истории.

Для временного отключения пользователя и удаления сессий:

```sql
begin;
update checklist_private.users set enabled=false where user_key='agnesa';
delete from checklist_private.sessions where user_key='agnesa';
commit;
```

## Доступ и правила

- PIN проверяется на сервере; пять неправильных попыток блокируют аккаунт на 15 минут. Счётчик защищён блокировкой строки от параллельного перебора. Это лимит по аккаунту: чужие неудачные попытки могут временно заблокировать вход. Для публично рекламируемого URL дополнительно нужны лимиты/защита на API-шлюзе.
- Сессия — случайный 256-битный непрозрачный token на 12 часов; в БД только SHA-256. Роль и имя на каждом запросе читаются из закрытой таблицы. Выход удаляет сессию. Изменение браузерного localStorage не даёт полномочий.
- Сотрудник читает только свои записи и изменяет только сегодняшний день. Владелец читает всех, но не отмечает задачи от имени сотрудника.
- Дата и время записей, дедлайны 10:00 / 20:00 и 60 секунд для отмены вычисляются сервером в `Europe/Moscow`. Поле `date` клиента проверяется на совпадение; при смене дня возвращается `DATE_CHANGED`.
- ID, название и секция задачи берутся из серверного каталога. `m9` / `e8` доступны после остальных пунктов секции, включая пункты с причиной невыполнения. Отмена предыдущего пункта требует сначала отменить подтверждение.
- Уход возможен только после прихода. Нельзя отменить приход при существующем уходе.
- Повтор записи не меняет время; изменение уже сохранённой отметки требует отмены. Идемпотентность покупателей — по `eventId` (UUID), повтор сохраняет одного посетителя. Клиент должен сохранять тот же UUID при повторе неясного результата.
- На таблицах включён RLS, нет разрешающих browser-политик и грантов. Privileged функции размещены в закрытой схеме с пустым `search_path`; только три анонимные публичные обёртки разрешены и внутри проверяют PIN либо непрозрачную сессию. Здесь используется собственная PIN-сессия, а не Supabase Auth JWT / `auth.uid()`.

## Контракт RPC

Все методы — `POST /rest/v1/rpc/<имя>` с `apikey: <publishable key>` и JSON. Служебные уведомления отдельно, недоступны браузеру. Бизнес-ошибка может иметь HTTP 200, поэтому клиент обязательно проверяет `success`.

| Метод | Параметры | Результат |
|---|---|---|
| `checklist_login` | `p_user_key`, `p_pin` | `{success, token, expiresAt, user:{key,name,role}}` |
| `checklist_request` | `p_token`, `p_action`, `p_payload` | см. действия ниже |
| `checklist_logout` | `p_token` | `{success:true}` |

Действия: `get_day {date}`; `complete_task {date,taskId}`; `fail_task {date,taskId,reason}`; `undo_task {date,taskId}`; `work_status` / `undo_work_status {date,status:'arrive'|'leave'}`; `log_customers {date,eventId}`.

Чтение возвращает `{success:true,date,tasks,customersLog,serverTime}`. Ключ tasks — `имя_сотрудника_taskId`. Отметка возвращает `{success:true,date,entry,timeStr,isLate}`; отмена — `entry:null`. Покупатель — `{success:true,date,entry:{id,employee,timestamp,timeStr},timeStr}`. Ошибка — `{success:false,code,error}`, иногда `retryAfter` (секунды) или актуальная `date`.

## Telegram (необязательный серверный worker)

Сохранение отметок работает без Telegram. Уведомления о приходе/уходе, дневных пунктах и подтверждении утренней/вечерней секции попадают в закрытую очередь в той же транзакции, что и запись. Через 65 секунд их можно отправлять: отменённые за разрешённую минуту записи удаляются из очереди. Уведомление о подтверждении содержит число выполненных/невыполненных пунктов и причины. Отдельного сообщения на каждый утренний/вечерний пункт нет.

1. **Отзовите старый опубликованный bot token через BotFather.** Удаление из текущего JavaScript не отзывает токен из истории Git.
2. Разверните Edge Function `functions/checklist-notify/index.ts` вместе с `handler.mjs`. При использовании CLI сначала откройте `supabase --help`, затем справку `supabase functions deploy --help` и `supabase secrets set --help` установленной версии. Конфигурация функции уже содержит `verify_jwt=false`: доступ вместо JWT защищает отдельный секрет планировщика, минимум 32 символа. Функция возвращает 503 при неполной конфигурации и 401 при неверном секрете.
3. В **Edge Function Secrets**, не в браузере, задайте `TELEGRAM_BOT_TOKEN`, `TELEGRAM_OWNER_CHAT_ID`, `CHECKLIST_CRON_SECRET`. Сгенерируйте последний криптографически случайным. Supabase предоставляет `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` в серверной среде; убедитесь в их наличии.
4. В доверенном планировщике создайте вызов раз в минуту: `POST https://<project-ref>.supabase.co/functions/v1/checklist-notify`, заголовок `x-checklist-cron-secret: <секрет>`, тело `{}`. Храните секрет в хранилище планировщика или Supabase Vault. Не встраивайте такой вызов в GitHub Pages / service worker. Пока расписание не настроено, очередь сохраняется, но сообщения **не отправляются**.
5. Проверьте доставку одного тестового события в согласованный чат. Ответ worker содержит только `{delivered,failed}`. В этой доработке реальные сообщения не отправлялись.

Worker арендует до 20 сообщений на 3 минуты; сбои повторяются через 5 минут, максимум 10 попыток. Политика доставки — **как минимум один раз**: если Telegram принял сообщение, а подтверждение в БД потерялось, повтор возможен. Вызов Telegram использует обычный текст, без HTML-интерпретации причин.

Диагностика из SQL Editor:

```sql
select id, created_at, attempts, available_at, sent_at
from checklist_private.notification_outbox
where sent_at is null order by created_at;
```

После устранения причины ошибки оператор может повторно поставить сообщения с исчерпанными попытками:

```sql
update checklist_private.notification_outbox
set attempts=0, available_at=now(), claimed_until=null, claim_token=null
where sent_at is null and attempts>=10;
```

## Локальная проверка

Из корня проекта: `npm ci`, затем `node --test supabase/tests/*.test.mjs`. Тесты поднимают временный PostgreSQL WASM (PGlite) с реальным pgcrypto, применяют SQL, вызывают RPC от `anon`/`authenticated`/`service_role`, проверяют миграцию старой схемы, доступ, PIN, лимиты, сессии, роли, бизнес-правила, повторы и очередь. Доставка Telegram проверяется с подставленным HTTP transport; настоящие сообщения не отправляются.

Это не заменяет проверку после установки в Supabase: сетевые разрешения, Data API, Edge runtime и планировщик проверяются отдельно. Запустите Supabase Security Advisor после установки; закрытые таблицы с RLS без политик здесь намеренно недоступны браузеру. Проверка на staging: прямой SELECT/INSERT/DELETE через publishable key должны отказать; RPC с неверной сессией — `UNAUTHORIZED`; сотрудник не должен увидеть второго сотрудника. Не отключайте RLS для устранения ошибок конфигурации.
